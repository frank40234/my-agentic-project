# 遊戲開發領域規範

## 架構模式

- 優先採用 **Entity-Component-System（ECS）** 架構：
  - **Entity**：純粹的 ID，不包含邏輯或資料
  - **Component**：純資料容器，不包含行為邏輯
  - **System**：處理擁有特定 Component 組合的 Entity，包含所有邏輯
- **組合優於繼承**：透過掛載不同 Component 組合來定義實體行為，禁止深層繼承樹
- 使用**有限狀態機（FSM）** 或**階層式狀態機（HFSM）** 管理遊戲流程：
  - 場景切換（主選單 → 遊戲中 → 暫停 → 結算）
  - AI 行為（巡邏 → 追擊 → 攻擊 → 撤退）
  - 角色狀態（待機 → 移動 → 攻擊 → 受傷 → 死亡）
- 每個 System 只負責單一職責，禁止在一個 System 中處理不相關的邏輯

## 遊戲迴圈

- **物理與邏輯更新**：使用固定時間步長（Fixed Timestep），典型值為 `1/60` 秒
  ```
  accumulator += deltaTime
  while (accumulator >= fixedStep):
      updatePhysics(fixedStep)
      accumulator -= fixedStep
  ```
- **渲染**：使用可變時間步長，以最大幀率渲染
- 物理更新與渲染之間使用**插值（Interpolation）** 避免畫面抖動
- 禁止在渲染邏輯中修改遊戲狀態
- 明確區分 `Update`（每幀）與 `FixedUpdate`（固定步長）的用途

## 資源管理

### 物件池（Object Pool）

- 頻繁建立 / 銷毀的物件必須使用物件池：
  - 子彈、粒子特效、敵人、撿取物
- 物件池在場景初始化時預先配置
- 歸還物件時必須重設狀態，避免殘留資料

### 延遲載入（Lazy Loading）

- 大型資產（音樂、高解析度貼圖、關卡資料）使用延遲載入
- 搭配載入畫面或背景串流載入，避免卡頓
- 資產使用引用計數或標記機制追蹤使用狀況

### 記憶體管理

- 場景切換時主動釋放不再需要的資源
- 監控記憶體使用量，設定資產快取上限
- 使用資源管理器集中管理所有資產的載入與釋放

## 輸入處理

- 實作**輸入緩衝（Input Buffer）**：
  - 格鬥 / 動作遊戲：緩衝 3～10 幀的輸入，允許提前輸入
  - 避免因幀率波動導致操作遺失
- 使用**指令模式（Command Pattern）** 解耦輸入與行為：
  ```
  InputMapper → Command → Entity
  ```
  - 輸入映射層將硬體輸入轉換為邏輯指令
  - 指令物件封裝行為，支援重播（Replay）和撤銷（Undo）
- 支援多種輸入裝置（鍵盤、手把、觸控）的抽象映射
- 輸入設定必須可由玩家自訂（Key Rebinding）

## 效能最佳化

### 記憶體配置

- **禁止在每幀（Update）中配置記憶體**，避免 GC 壓力：
  - 禁止在迴圈內 `new` 物件
  - 使用預分配的集合與緩衝區
  - 字串操作使用 `StringBuilder` 或等效工具
- 快取頻繁存取的 Component 參照，避免每幀查詢

### 空間分割

- 碰撞偵測與範圍查詢必須使用空間分割結構：
  - **2D 遊戲**：Quadtree 或 Grid
  - **3D 遊戲**：Octree 或 BVH（Bounding Volume Hierarchy）
- 禁止對所有實體做 O(n²) 暴力碰撞檢測

### LOD（Level of Detail）

- 依據攝影機距離切換模型 / 貼圖精細度
- 遠處物件使用簡化模型或 Billboard
- LOD 切換必須平滑，避免明顯的跳變

### 批次渲染（Batching）

- 使用相同材質的物件合併為批次繪製
- 減少 Draw Call 數量
- 靜態物件使用 Static Batching，動態物件使用 Dynamic Batching 或 GPU Instancing

## 網路同步（多人遊戲）

- 採用 **Client-Server 架構**，伺服器為權威端：
  - 客戶端發送輸入，伺服器計算結果
  - 禁止客戶端直接決定遊戲邏輯結果（防作弊）
- **客戶端預測（Client-side Prediction）**：
  - 客戶端立即執行本地輸入的預測結果
  - 收到伺服器回應後進行校正
- **伺服器回溯（Rollback）**：
  - 伺服器收到延遲輸入時，回溯到該時間點重新模擬
  - 適用於即時性高的遊戲（格鬥、FPS）
- **狀態快照插值（Snapshot Interpolation）**：
  - 客戶端緩衝多個伺服器快照
  - 在快照之間插值渲染，提供平滑視覺效果
- 網路封包大小最佳化：只傳輸差異（Delta Compression）

## 資料驅動設計

- 所有遊戲數值**外部化**存放：
  - JSON / CSV / YAML / ScriptableObject 等格式
  - 包含但不限於：角色屬性、武器傷害、敵人 AI 參數、關卡配置
- **禁止在程式碼中硬編碼遊戲參數**：
  ```
  // ❌ 禁止
  float damage = 25.0f;

  // ✅ 正確
  float damage = weaponConfig.baseDamage;
  ```
- 支援熱重載（Hot Reload）：修改資料檔後無需重新編譯即可生效
- 資料檔案必須有 Schema 驗證，載入時檢查格式正確性

## 測試

### 自動化功能測試

- 必須涵蓋以下場景的自動化測試：
  - 場景載入與切換（不崩潰、不記憶體洩漏）
  - 存檔 / 讀檔（資料完整性）
  - 核心遊戲機制（傷害計算、碰撞判定、狀態轉換）
- 使用錄製重播（Record & Replay）驗證遊戲邏輯一致性

### 效能基準測試

- 建立效能基準：
  - 目標幀率（如 60 FPS）下的最大實體數量
  - 場景載入時間上限
  - 記憶體使用量上限
- 持續整合中加入效能回歸測試，超過閾值即報警
- 使用 Profiler 定期檢查熱點，禁止盲目最佳化
